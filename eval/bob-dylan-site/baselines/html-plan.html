Bob Dylan, Interactively

A plan for a mobile-first site where you explore Dylan's eras, albums, and songs the way a fan would trace them on a wall of index cards and string — by connection, not just chronology.

01

Overview & Goals

What "more engaging than Wikipedia" actually means, and the principles that keep the build honest about scope.

  • Explore by connection, not just by scrolling. The hook of Dylan's career is how everything reconnects — a 1963 protest song becomes a 1979 gospel reworking becomes a 2020 callback. The site's signature feature is a connections web, not another long-form article.
  • Three altitudes, always reachable in one tap: Era → Album → Song. You should never be more than a couple of taps from "play this in my head" context: what it sounded like, why it mattered, what it led to.
  • Phone is the primary device. Desktop gets a wider layout; it does not get a different app. Every interaction is designed thumb-first (swipe, tap, bottom sheets) and only enhanced for larger screens.
  • Curated over exhaustive. Dylan has 40+ studio albums and 600+ songs. A site that tries to model all of it will ship nothing. v1 covers ~10 eras, ~24 albums, ~70 songs, and ~120 hand-picked connections — enough for the web view to feel alive, not enough to become a maintenance project.
  • No backend. Everything is static files + a JS data object, so it can be hosted anywhere (GitHub Pages, Netlify, a single S3 bucket) with zero server cost or moving parts.

Architecture

A static site with one data module, one small app shell, and five view renderers. No framework, no bundler — plain ES modules the implementer can open and read top to bottom.

Flat file set, one-way data flow down, one feedback path up. No view ever talks to another view directly — everything routes through the store.

2 · router.js — the whole app's control flow
import { render } from "./util/dom.js";
import * as views from "./views/index.js";

const routes = [
  [/^#\/$/,                    views.timeline],
  [/^#\/era\/([\w-]+)$/,       views.era],
  [/^#\/album\/([\w-]+)$/,     views.album],
  [/^#\/song\/([\w-]+)$/,      views.song],
  [/^#\/web\/([\w-]+)$/,       views.connectionsWeb],
  [/^#\/search$/,              views.search],
];

function resolve() {
  const hash = location.hash || "#/";
  for (const [pattern, view] of routes) {
    const match = hash.match(pattern);
    if (match) {
      render(document.getElementById("app"), view(...match.slice(1)));
      return;
    }
  }
  render(document.getElementById("app"), views.notFound());
}

window.addEventListener("hashchange", resolve);
window.addEventListener("DOMContentLoaded", resolve);
3 · graph layout — cheap, deterministic, no physics library
// Places 1 center node + up to 6 neighbors on a circle.
// Deliberately not a full force simulation: with ≤7 nodes
// visible at once, a fixed radial layout is faster, more
// predictable to test, and never jitters on a slow phone.
export function layoutGraph(centerId, edges, radius = 110) {
  const neighbors = edges.filter(e => e.from === centerId || e.to === centerId);
  const step = (Math.PI * 2) / Math.max(neighbors.length, 1);

  return {
    center: { id: centerId, x: 0, y: 0 },
    nodes: neighbors.map((e, i) => ({
      id: e.from === centerId ? e.to : e.from,
      type: e.type,
      x: Math.cos(i * step) * radius,
      y: Math.sin(i * step) * radius,
    })),
  };
}

Risks

Ranked by what's most likely to derail the build or embarrass the launch.

RiskLikelihoodImpactMitigation
Album art / audio copyright. Can't legally host cover images or stream tracks. High High v1 ships CSS-generated gradient "covers" per album (palette keyed to era). Audio is link-out only, to official Spotify/YouTube. Lyrics limited to short excerpts (fair use), never full text.
Scope creep. "Just add one more album/song" compounds fast across 600+ real songs. High Med Hard cap for v1: 10 eras / 24 albums / 70 songs / 120 edges, fixed before Phase 1 starts. Data schema is designed to extend later without a rewrite.
Factual accuracy. Dylan's history is contested and dates/quotes are easy to get subtly wrong. Med Med Every era/album fact cross-checked against 2 sources minimum during Phase 0; sources logged next to the data, not just in someone's head.
Connections graph performance on low-end phones if node/edge count grows. Med Med Fixed radial layout (not a physics simulation), capped at 1-hop/≤7 visible nodes per screen. Tested on a mid-tier Android device, not just desktop DevTools throttling.
Accessibility gaps in the bottom sheet and graph (focus trap, contrast, motion). Med Med prefers-reduced-motion respected everywhere; focus trapped inside open sheets; graph nodes reachable and operable via keyboard, not tap-only. Verified with VoiceOver + TalkBack in Phase 7.
Browser quirks — iOS Safari scroll-snap and hash-routing edge cases. Med Low Real-device test pass in Phase 7 on iOS Safari + Android Chrome specifically, not just desktop emulation.
Link rot on outbound Spotify/YouTube "listen" links. Low Low All links live in data.js in one place, so a broken link is a one-line fix, not a hunt through markup.

Open Questions

Decisions worth 30 seconds of your input before Phase 1 starts — everything else in this plan can proceed without them.

  • Hosting target? Assuming GitHub Pages or Netlify (free, static, matches the no-backend approach) unless you have a preference.
  • Embed Spotify/YouTube players inline, or link out? Plan assumes link-out (simpler, no iframe/consent complexity, no autoplay policy fights on mobile).
  • Exact era/album/song list? The 10 eras above are a reasonable spine; final album/song picks happen in Phase 0 and are worth a quick sanity check from you first.
  • Any songs/eras you'd consider non-negotiable? (e.g. "Blowin' in the Wind," the Newport '65 moment) — good to flag before the curation pass so nothing obvious gets cut for space.
