# SCRIPT — close-the-lifecycle (four parts)

**Voice:** am_michael (Kokoro, local; synthesised at speed 1.25)
**Voice settings:** default
**Voice direction:** Plain and even. A good teacher explaining a plan to a peer: one idea per sentence, an example for every mechanism, a comparison for every choice.

---

## Line 1 — Approved, and then nothing (Frame 1)

**Delivery:** Plain.

    A reviewer approves a plan and makes three calls on it. Then an agent writes the code, and nothing checks that the code keeps those calls.

## Line 2 — Today: the review loop (Frame 2)

**Delivery:** Plain.

    Today, reelplanning covers the first half. You decide in the review player, resolve-plan and the reel CLI record your calls, the revise step rewrites the plan, and plan-diff offers only the beats that changed.

## Line 3 — The missing half, and 3 new parts (Frame 3)

**Delivery:** Plain.

    The second half is missing. Nothing holds the code to the plan, a flagged call goes nowhere, and a newcomer has nothing to watch. This plan adds the implement step, the walkthrough fix step and the system video, and joins them into a build loop.

## Line 4 — Step 1: the system video (Frame 4)

**Delivery:** Plain.

    Step one, the system video. A new system mode turns the spec, the system map and the glossary into one video for someone new: purpose, parts, pipelines, invariants. Every frame is tagged with the spec section it explains, so a later change can find its frames.

## Line 5 — Step 2: implement, and log each call (Frame 5)

**Delivery:** Plain.

    Step two, the implement step. The agent builds from the resolved plan, with the decisions in force as rules, not suggestions. Each call the plan did not cover, like returning four-oh-nine instead of four hundred, goes into the autonomy log the moment it is made. A call is a choice you could have made the other way, like a default or a library, never a variable name. One row per choice; past about a dozen, the plan left too much open.

## Line 6 — Next: part 2 (Frame 6)

**Delivery:** Plain.

    Next, part two: who checks the code, and the walkthrough.

## Line 7 — Part 2 of 4 (Frame 7)

**Delivery:** Plain.

    Part two of four. The code is written, and every call it made is logged. Now, who checks it?

## Line 8 — Step 3: check the diff first (Frame 8)

**Delivery:** Plain.

    Step three: check the diff before any video is built. First, reel audit fails when a plan step has no entry in the report. Then a second agent reads the diff, as you decided in the review. It is a fresh, separate run that holds only the plan, the ledger and the diff. The orchestrating session starts it, never the implementer, so it cannot inherit the implementer's reasons.

## Line 9 — Step 4: walk through the real code (Frame 9)

**Delivery:** Plain.

    Step four: the walkthrough is built from that report, with the existing walkthrough mode, on the same stage as the plan video. Every logged call becomes an Accept or Flag beat, and every deviation is said plainly. It is the first walkthrough of code an agent really wrote.

## Line 10 — Next: part 3 (Frame 10)

**Delivery:** Plain.

    Next, part three: what happens to a flagged call.

## Line 11 — Part 3 of 4 (Frame 11)

**Delivery:** Plain.

    Part three of four. The walkthrough has been watched, and every logged call has a verdict.

## Line 12 — Step 5: act on the verdicts (Frame 12)

**Delivery:** Plain.

    Step five: act on the verdicts. An accepted call becomes a ledger entry, so the next plan cannot quietly undo it. A flagged call goes to the walkthrough fix step, which rewrites the code and rebuilds only that beat, as you decided. And a comment that would overturn a ledger decision is not fixed in place: it becomes a new plan.

## Line 13 — Next: part 4 (Frame 13)

**Delivery:** Plain.

    Next, the last part: keeping the system video current.

## Line 14 — Part 4 of 4 (Frame 14)

**Delivery:** Plain.

    Part four of four. Flags are fixed, and accepted calls are in the ledger.

## Line 15 — Step 6: keep the system video current (Frame 15)

**Delivery:** Plain.

    Step six. After every accepted walkthrough, as you decided, the agent updates the spec for what landed, and the system video rebuilds only the frames tagged with what changed. It has to stay cheap. The text is updated in the background, so the video is always ready to build. Only the changed lines get new narration. And nothing renders until someone asks.

## Line 16 — The plan, resolved (Frame 16)

**Delivery:** Plain.

    That is the plan: six steps, and the three calls you made, now in force. Draw on any step to ask for a change, or approve it.
